# 10,000 requests, 200 rendered rows

The original list rendered every request after each filter or selection. A local stress experiment exposed substantial automation-observed filter latency at 10,000 requests. The list now renders a page of at most 200 rows. Filtering and sorting still run over every matching request; statistics and export still use the full capture.

## Recorded runs

Same synthetic HAR, same machine, Chromium `155.0.8059.40`, production Vite builds served on localhost. Three trials per version, with page reload before each trial. CPU: Apple M5 Pro; macOS 26.5.2; Node 26.8.2.

| Measure | Original `3d14dbf` | Paged implementation |
|---|---:|---:|
| Request buttons after import | 10,000 | 200 |
| Import observation, median | 415 ms | 76 ms |
| Filter observation, median | 5,199 ms | 9 ms |

All samples, including the slower first paged import, are preserved in [before](stress-before.json) and [after](stress-after.json). The fixture SHA-256 matches in both runs.

These are **automation-observed durations**, including Playwright protocol, locator resolution and rendering. Import ends after the capture heading appears and two animation frames pass. Filtering begins before filling `/9999` and ends when the matching request button is found. The numbers are not isolated JavaScript timings, an INP measurement, or a production speedup guarantee. A smaller DOM can accelerate the test tool's locator work as well as the UI itself. Only three samples on one machine were taken, without randomized run order.

The reliable structural result is the bound: at most 200 request buttons exist at once. Pagination tests walk all 20,000 supported entries without losing or repeating an ID. Browser checks reach the final partial page, search for a request outside page one, sort globally, and export every record while only one filtered row is visible.

## Reproduce

```sh
npm ci
npm run build
npm run preview -- --port 4320
# In a second terminal:
node --experimental-strip-types scripts/measure-ui.mjs \
  http://127.0.0.1:4320/ output/playwright/my-result.json
```

The optional experiment uses `npx @playwright/cli` and an isolated named browser session. If the CLI asks to install its browser, run its `install-browser` command once. You may set `PLAYWRIGHT_CLI` to a local wrapper executable. The runner generates the deterministic synthetic HAR and refuses to overwrite a result file. It is not run as a timing threshold in CI; shared-runner timing would be unreliable.

For the original comparison, build commit `3d14dbf` in a separate checkout and point the **current** runner at that preview URL. Use a separate result path. No production request is generated by the stress fixture.

The browser regression flow is also saved in `scripts/check-ui.js`. With the preview open in Playwright CLI, run `playwright-cli run-code --filename scripts/check-ui.js`. It verifies page boundaries, global search/sort/filter, keyboard activation, full-capture JSON export, malformed imports and both examples.
